# Final Project Proposal

**Log-Polar Video Feedback Driven by Live System Telemetry**
A file browser whose visual field is a video-feedback system modulated by measured
activity inside the computer running it.

Shashank · CSVAD Fall 25

---

## 1. What it does

A full-screen file browser. The user navigates directories by tap-and-slide: touching an
item and sliding expands it, revealing its children; sliding further descends another
level. Layout is generated, not drawn — directories are laid out by a space-colonization
algorithm with phyllotactic leaf placement, so branching geometry is a function of actual
directory structure.

The entire field is rendered through a video-feedback loop: each frame samples the
previous frame through a small affine warp, adds new content, and applies a nonlinearity.
The parameters of that loop — zoom rate, rotation rate, feedback gain, diffusion radius,
hue rotation — are not authored constants. They are control signals derived, by the
analysis described in §4, from live measurements of the machine: CPU occupancy, page
fault rate, disk transactions, network throughput and retransmissions, battery
temperature, filesystem events, and the user's own cursor and scroll behaviour.

The pattern generator runs in **log-polar coordinates**. The retinocortical map is
approximately `(r, θ) → (log r, θ)`, so a plain sinusoidal grating in that space renders
on screen as a concentric tunnel, a radial fan, or a logarithmic spiral depending only on
the grating's orientation, and a hexagonal lattice renders as a rosette. Figure 1 shows
all four produced by one generator with only `(k₁, k₂)` varied. Zoom-based video feedback
is a constant translation in the same coordinates, which is why feedback produces tunnels.
Generating in log-polar space and warping the feedback accumulator in log-polar space are
therefore the same operation, and the system does both.

Two loops close. The rendered frame is read back and analysed, and its own spectrum
controls the feedback gain (§4, ops 11–13). Separately, the renderer's GPU cost appears in
the telemetry that drives the renderer, so the piece is measurably self-referential.

## 2. Current state

Built and running:

- `telemetryd.js` — dependency-free daemon sampling **43 channels at 30 Hz** from seven
  unprivileged sources (`vm_stat`, `iostat`, `nettop`, `ioreg`, FSEvents, `top`, and a
  native probe). Serves SSE and records NDJSON. Measured cost ~2% of one core.
- `pressure-probe.swift` — AppKit input probe (cursor, scroll, clicks, Force Touch
  pressure) in three capture modes.
- `scope.html` — 43-channel live oscilloscope with four scaling modes.
- `figures/make-formconstants.js` — the Figure 1 generator.

Not built: the renderer, the DSP chain, the navigation.

Empirical findings so far that constrain the design: analog Force Touch pressure is only
delivered to the application under the cursor, not system-wide (verified over 2,267
captured events), so slide distance rather than pressure is the primary continuous input;
`powermetrics` and `fs_usage`, the two highest-rate sources, require root and are
therefore excluded from the live path.

## 4. Signals and the processing applied to them

Sources are the 43 measured channels, the rendered frame buffer, and the filesystem graph.
Rows marked ▸ are the ones I consider load-bearing rather than ornamental.

| # | Tool | Input signal | Operation | Drives |
|---|---|---|---|---|
| 1 | conditioning | all counter channels | differentiate → `log1p` → detrend → Hann window → resample to a uniform grid | prerequisite for everything below |
| 2 ▸ | **STFT** | `cpu.busy_pct`, `disk.tps` | 1–4 s window, 50% hop; spectral centroid and flatness | diffusion radius (blur) in the feedback kernel |
| 3 ▸ | **STFT → iSTFT** | `net.in_bytes_per_s` | band-select 0.1–0.3 Hz (respiration band), resynthesize | the slow "breathing" envelope modulating zoom rate |
| 4 ▸ | **autocorrelation** | `vm.faults_per_s` | detect periodicity of build / GC / indexing cycles | rhythm of impulse injection into the field |
| 5 | **autocorrelation** | `in.cursor_speed` | estimate the user's own gesture tempo | phase-locks the visual pulse to the user's rhythm |
| 6 ▸ | **cross-correlation** | `disk.tps` × `vm.faults_per_s` | lag search 0–5 s: which subsystem leads | orders visual events causally instead of simultaneously |
| 7 ▸ | **cross-correlation** | `in.cursor_speed` × `cpu.busy_pct` | does user action precede machine load? | gates the self-referential loop; sets its sign |
| 8 | **digital filters** | `net.*`, `in.cursor_*` | one-pole IIR envelope follower (separate attack/release); one-euro filter on cursor | advection gain; jitter-vs-lag control |
| 9 ▸ | **convolution (1-D)** | `net.retx_per_s`, `fs.events` | sparse event train ⊛ exponential decay kernel | continuous excitation envelope from discrete events |
| 10 ▸ | **convolution (2-D)** | feedback accumulator | Gaussian blur = diffusion term; unsharp mask = reaction term | makes the accumulator a reaction–diffusion system |
| 11 ▸ | **2-D FFT** | rendered frame | radially averaged power spectrum; detect spectral collapse (saturation) or flatness (noise) | automatic gain control holding the loop at edge-of-chaos |
| 12 ▸ | **FFT → iFFT (phase correlation)** | frames *t*, *t−1* | cross-power spectrum → iFFT → peak = global shift/rotation | optical flow for advection; closed-loop check that the achieved warp equals the intended warp |
| 13 ▸ | **FFT (1-D)** | frame resampled to log-polar | FFT along the angular axis; dominant angular wave number | measures and then steers the symmetry order — the number of spiral arms |
| 14 | — | filesystem graph | depth, fan-out, `mdls` metadata, content entropy | space-colonization attractor placement; not a time series |

Operations 11–13 are the ones I am least sure about and most interested in: they apply
analysis to the work's own output and feed the result back as control, rather than
analysing an external signal.

## 7. Questions

1. **Scope.** This is arguably two projects: a navigable browser and a telemetry-driven
   feedback visualizer. Should I cut the navigation entirely and submit the visualizer,
   keeping the browser as the frame it sits in? I would rather cut now than at week 5.
2. **Ops 11–13.** Is applying FFT analysis to the work's *own rendered output* and feeding
   the result back as a control parameter a legitimate use of the class's tools, or does
   it read as control engineering rather than signal processing?
3. **Phase correlation.** Is FFT-based phase correlation (op 12) an acceptable substitute
   for a classical optical-flow method, given it is built from FFT/iFFT?
4. **Irregular sampling.** Telemetry arrives at 0.5–30 Hz, some of it event-driven and
   genuinely non-uniform, while frames run at 60 Hz. Is resampling onto a uniform grid
   before STFT acceptable, or do you want Lomb–Scargle on the irregular channels?
5. **Window length.** These signals are non-stationary on a ~1 s scale, but at 1 Hz
   sampling a 4 s window gives very few bins. Is there a preferred approach here —
   multirate analysis, per-channel window lengths, or should I simply sample faster
   (several sources will go to 100 Hz+ if I run the daemon as root)?
6. **Evidence.** What would convince you the signal processing is load-bearing rather
   than decorative? I was planning ablations — the same capture rendered with each
   operation disabled — but that doubles the render work.
7. **Is the log-polar transform a signal-processing tool in this class's sense** (a
   coordinate transform applied before filtering, as in a Mellin transform), or should I
   present it purely as rendering?
8. **Deliverable.** Live application, recorded capture, or both? The live version needs
   macOS and, for one optional input, a Force Touch trackpad. I can ship a version driven
   by pre-recorded NDJSON for reproducibility — would you prefer that for grading?
9. **Photosensitivity.** I am limiting to ≤3 flashes/s (WCAG 2.3.1) and honouring reduced
   motion. Is there an institutional requirement for exhibition beyond that?

## 8. Deliverables

Source (daemon, shader, DSP chain), a reproducible figure set, a recorded capture with the
driving telemetry included as NDJSON so any frame can be traced back to the measurements
that produced it, and the LLM conversation logs.
